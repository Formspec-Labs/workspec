# Notice requirements and supported execution

This matrix interprets [Governance §3.2](workflow-governance.md#32-notice) for the maintained native and server notice owners. It separates declaration validity, installed transport support and qualification of an individual retained result. It does not establish legal delivery or qualify a deployment.

## Normative Contract

The canonical [notice-requirements schema](../../schemas/wos-notice-requirements.schema.json) declares exactly one `observation`, `scope` and `anchor` for each selected binding in [GovernancePolicyRules v2](../../schemas/wos-governance-policy-rules.schema.json). The four declaration methods are `transportAccepted`, `providerDelivered`, `openObserved` and `recipientAcknowledged`; they are distinct observations with no implicit substitution. SMTP acceptance establishes only `transportAccepted`.

The selected D1 send-sufficient policy follows these same rules: documented successful sending is sufficient, while recipient receipt, opening and acknowledgment are not prerequisites. Stronger declarations remain valid vocabulary and require an adapter that actually establishes their exact observation and scope; the maintained SMTP host does not install those methods. Selecting one refuses with `NOTICE-004` at the affected requirement location, rather than downgrading to SMTP acceptance.

## Composition

The [Workflow adverse-policy schema][A] encodes required notice timing. The shared core predicates `check_notice_declaration`, `check_adverse_notice_timing` and `check_notice_support` [C] validate meaning and installed support. Actual binding uses determine the consequence; an informational label cannot weaken a deadline or adverse-effect use. [Governance policy analysis][G] and contextual lint apply those predicates to the exact Workflow, original Rules and separately selected IntegrationProfile.

The server's [`LoadedNotices::check_requirements`][S] checks installed capability and exact native/host selections before activation. [`SelectedNoticePolicy`][HP] checks individual retained send success and request identity. The checked-send runtime owner [N], callback owner [CB] and governed clock owner [T] retain the original invocation, intent, attempt, case/process, recipient, content, policy, observation and time associations. Neither a structurally valid result nor a caller-supplied timestamp grants evidence authority.

Observation qualification and printed-date qualification are separate checks. The same selected clock owner maps the physical observation into governed case time. `observation_qualified` supplies that required original anchor without asserting a printed absolute deadline; `date_agreement` additionally binds the rendered date to the independently recomputed original-observation deadline. [Kernel §9.7.2](../kernel/spec.md#972-timer-creation) uses that governed origin. This distinction changes no authored period, calendar, unrelated timer basis or retained historical record.

## Conformance

The linked controls are executable tests and source references, not a claim that they ran for every deployment. A verification receipt must record the exact checkout, selected features, command, count, result and unmodified output. In particular, `governance_deser` contains four tests; it is a deserialization check, not a notice-delivery journey.

Full host acceptance still requires the selected deployment's artifacts and installed adapter to pass admission, actual retained successful sending, delayed callback and restart checks. A same-session browser check must inspect rendered notice content and acceptance across the relevant date boundary. Software fixtures and native checks do not establish those deployment/browser results or production recipient delivery. Failed, unknown, missing-clock, unsupported-method and date-disagreement controls remain required alongside the positive send-sufficient path.
